## 2. Lab code that could not produce its promised result

- **The regression gate that cannot fail** — `eAIS/labs/guardrail-evaluation-lab.md`. It was
  invoked with `--baseline baseline.json --current baseline.json` while `harness.py` rewrote
  that same file on every run. The harness now writes its own metrics file and the CI example
  compares two distinct files. The lab still says, twelve lines earlier, that a baseline which
  follows the current code always passes: that sentence is now true of the example.
- **A sanitiser that removed the attribute, not the text** — `eAIS/labs/injection-lab.md`. The
  hidden channel survived in the chunk while the drill asked the reader to list the channels
  they had removed.
- **A filter declared fail-closed that opened on a null identity** —
  `eAIS/labs/rag-data-leakage-lab.md`. A null tenant matched every unclassified chunk.
- **An FGSM fragment that could not run with either type** —
  `eAIS/methodology/04-adversarial-attacks.md` mixed numpy and torch APIs.
- **A YARA rule that could never match the file the drill used** —
  `eSOC/tools/detection-rules/yara-rules/yara-example.yar` required `pe.is_pe` while the drill
  ran it against a `.txt`. Executed proof: the old rule produced **no output** for a text file
  with three of its strings and **did** match the same content appended to a PE; the rule added
  for the text drill matches the `.txt`, and a file that merely starts with `MZ` fires only
  that one.
- **A beacon filter that measured the bucketing, not the jitter** — eSOC's SPL binned `_time`
  before computing deltas, so every service looked perfectly regular. Same defect, same family,
  in eCTHP: the rule used absolute σ where the module itself defines the signal as σ/mean.
  Executed with synthetic logs: `jitter < 5` **admitted** noisy traffic (σ 2.3 s) and
  **rejected** a real slow beacon (σ 11.4 s, CV 0.019).
- **"Unique subdomains" that counted queries** — missing `sort -u` before the `awk`. Executed:
  one name repeated 50 times was reported as 50 subdomains.
- **A JavaScript hook that was a syntax error** — `eMAPT/methodology/04-communication-analysis.md`
  had `function (untrustedChain, ...)`. `node --check` on the old fragment: `SyntaxError:
  Unexpected token ')'`; on the replacement: exit 0.
- **A CL.TE payload whose prefix never left the front end** — `Content-Length: 4` over a
  29-byte body. Counted byte by byte, and the confirmation criterion now matches the payload.
- **An ID token authorised without validation** — `eIAMA/labs/iam-scenarios.md` decoded claims
  and trusted them. It now validates signature, `iss`, `aud`, `exp` and `nonce`, which the
  module's own cheatsheet already required. Executed with a local key as the realm's JWKS:
  the old callback accepted a forged signature, a wrong issuer, an expired token and an
  unsigned `alg=none` token; the corrected one rejects all four and accepts the valid one.
- **A harness that reported the inverse of what it measured** — `eAIS/labs/guardrail-evaluation-lab.md`
  assigned `decide()`'s "allowed" flag to `blocked`, so the lab printed the *allow* rate as the
  block rate and scored a control that blocks everything as 0. Found while verifying the two
  fixes above, because nothing else explained the numbers: with all checks enabled the harness
  reported `block_rate 1.0 / fp_rate 1.0`; with `--checks input` it reports `0.5 / 0.0`, and the
  format blocks (35) are now counted apart from the security blocks (15).
- **A Keycloak lab that the audit described too strongly** — the fix pass ran Keycloak 26.1.0
  three times (old variables, new variables, none) and **measured** the opposite of what the
  audit assumed: `KEYCLOAK_ADMIN*` is deprecated but still honoured, with
  `WARN KC-SERVICES0110` and a working admin login; with no variables at all the login returns
  401, so the test discriminates. The lab now uses `KC_BOOTSTRAP_ADMIN_USERNAME` /
  `KC_BOOTSTRAP_ADMIN_PASSWORD` because those are the supported names, and the note says
  "deprecated alias", not "broken".
- **Evidence written to the system under investigation** — eCIR's containment block and
  cheatsheet captured to `C:\` and to relative paths, against the module's own rule, before a
  reimage that would have destroyed the only copy.
- **A scanner that claimed not to follow redirects and did** — `urllib.request.build_opener`
  adds `HTTPRedirectHandler`, so the 301/302 branch was dead. Repaired in the code, and
  re-tested against a local server that redirects; the branch now fires.
- **A manifest that "verified the image" while hashing the source** — eCDFP's
  `sha256sum -c evidence-source.sha256` re-read the device. The flow now writes one manifest
  per artefact, each naming the file it describes.

## 6. Repository infrastructure and governance

- **The checker could not see four of the six defect classes its own header named.** It now
  reads fenced blocks in `bat`, `cmd`, `ps` as well as shell languages, inline code spans
  that look like a command (that is how the fourth `--no-pause`, inside prose, was found),
  and **tables of flags** when the table's context names exactly one catalogued tool — the
  shape that let `nmap -oJ` sit in a table for two audits. It accepts universal flags such as
  `--help`; knows which flags take a value, so `velociraptor -r Windows.System.Pslist` is not
  reported as an unknown plugin; skips audit records, which quote broken commands on purpose;
  and provides an explicit escape (`<!-- check-commands: ignore -->`) for a guide line that
  quotes a wrong invocation in order to warn about it. Both new behaviours were tested against
  a deliberately broken copy: an invented flag in a table makes the check exit 1, and the same
  row with the escape marker makes it exit 0.
  One blind spot remains and is stated in its header: `-oJ` is read as `-o` with the value `J`
  attached, because the same prefix rule is what accepts `-T4` and `-p80`. Real nmap does
  something worse than error — `nmap -oJ salida.json 127.0.0.1` writes a file called `J` and
  treats `salida.json` as a target — which is exactly why that row mattered.
- **A second check covers what no flag catalogue can.** `scripts/utilities/check-code.mjs`
  fails on a fenced block that is never closed (one shipped here, swallowing the last third of
  a file) and on any `python` or `js` block, or `.py`/`.mjs` file, that does not parse. It
  executes nothing: Python is parsed with `ast.parse`, JavaScript with `vm.Script`, and Python
  blocks are reported as skipped rather than passing on a machine without Python 3. Tested
  against a copy with four deliberate defects — an unclosed fence, a Python syntax error, a
  JavaScript `function (x, ...)` and a broken standalone script — it found all four and exited
  1.
- **The weekly external sweep could never pass**: three RFC 2606 placeholders (`*.example`)
  and the deliberately-dead `…/security/certifications` index were permanent failures. Both are
  now recognised: reserved names never fail, and a short documented list of URLs the repository
  cites *because* they are dead is skipped. The sweep now reports only real rot.
- **`tool-installer.py` ran the package name as the installer** (`apt` vs `apt-get`) and then
  printed `installed`. It now resolves the package per manager, refuses unknown tools, verifies
  the manager afterwards, and treats `--dry-run` as the default it always claimed to be.
- **`env-setup.sh` probed for a command that cannot exist** (`python3-pip`), so it reinstalled
  every time and aborted on managers that do not have that package; it also reported success
  with an unknown manager. It now separates commands from packages, stops on an unknown
  manager, and checks that the binary appeared.
- **`report-generator.py` showed "100%" for files with no checklist** and grouped every file
  into one module. It now reports `n/a`, groups by area/module, and states how many notes were
  excluded.
- **Twenty-five tool catalogues and two rewritten scripts were unpublished** in the working
  tree: that is why the published CI was green while the local checker reported 14 defects.
  They are published with this pass, so the check runs with the coverage it was written to have.
- **The root documents were out of step with the code**: `README.md` and `CONTRIBUTING.md` said
  "two checks" while CI runs three and now describe all three; `README.es.md` is labelled as an
  orientation page rather than a translation, and states where the figures live; `.gitignore`
  is commented in English as the project promises, with `node_modules/` added; the previous
  audit's summary table — five placeholder rows and a total that contradicted its own thirteen
  rows — was recomputed from the findings (112 entries: 21 Blocking, 57 Important, 33 Minor,
  1 Preference; 4 modules "not apt", 9 "with reservations").
- **How to say you checked something** is now a written convention, with the marker for
  counter-examples, and the checker measures adoption: it went from **0/162 files** to
  **78/165 (47%)** during this pass.

### 9.1 Every file that contains commands now says how it was checked

`check-commands.mjs` prints how many files carry a `> **Verification:**` record. That number
was **0/162** at the start of the first pass, **78/165** when it ended, **81/165** when the
second pass began, and is **163/163** now.
`.github/workflows/docs-check.yml` runs the check in its `--require-verification` form, so a
file that adds a command without saying what was done with it fails the build rather than
being counted quietly. The three forms the convention allows are in `CONTRIBUTING.md`:
*executed against `<tool> <version>` on `<date>`*, *checked against `<source>` on `<date>`*, and
*unverified syntax reference — not run*. The third is not a failure. It is the honest answer
for a lab that needs a SIEM, a domain, a hypervisor, a mobile device or a macOS host: of the
168 files that now carry a record, 86 describe an execution, 31 a comparison with primary
documentation, 43 state that nothing was run, and the remaining 8 describe a recomputation in
their own words. The checker counts 163 of those files as containing commands; the other five
carry a record even though it finds no command line in them — three module indexes, one tool
note whose blocks are sketches, and a reading list — and each of those records says what it
did check instead (the tree on disk, the link that had to resolve).

### 9.2 The checker learned two shapes and stopped inventing one

- **Tables of flags.** `| -oJ file | JSON |` in a note about nmap is a claim about nmap, and it
  is the shape that hid the `-oJ` defect across two audits. When a table's own context names
  exactly one catalogued tool, the flags in its cells are validated: 29 cells are checked on
  every run, a deliberately invented flag in such a table exits 1, and the same row with
  `<!-- check-commands: ignore -->` exits 0.
- **A diagram is not a command.** Both index pages draw the repository tree inside an
  unlabelled fence, and every line of the drawing was counted as a command line — which is why
  `README.md` and `README.es.md` looked like files that owed the reader a verification record
  for a directory listing. Box-drawing lines, `|--`/`` `-- `` tree lines and a bare `name/`
  line are now skipped. Verified both ways: a fence holding only a tree reports **0 command
  lines**, and a fence holding `cd payloads/` and `sudo nmap -sV 10.0.0.1` still reports 2, with
  the nmap line checked against its catalogue. No line that had been checked before stopped
  being checked.
- **`check-code.mjs` (added in the first pass) is now part of the gate**, so an unclosed fence
  or a block that does not parse fails CI. Its Python half parses with `ast.parse` on a runner
  that has Python 3; on a machine without it the blocks are reported as *skipped, never passed*,
  which is the wording that keeps a skip from reading as a pass. The difference is visible in
  the numbers: the same tree reports **12** blocks and files parsed on the Windows machine used
  for this pass and **61** in WSL, where Python 3.12.3 is on the PATH — and both runs are clean,
  so every `python` block and every `.py` file in the repository really does parse.

### 9.4 Findings that were wrong, and are recorded as wrong

- **Minor #8 named the wrong field.** `New_Process_Name` exists — the Splunk Add-on for
  Microsoft Windows extracts it, and `Parent_Process_Name` is the name that appears nowhere in
  the add-on. The finding was half right, and the half it got right had not been spotted:
  `Creator_Process_Name` is the real field, and that is what the query now uses.
- **`nmap -oJ` cannot be caught by this checker**, and saying so is better than tightening the
  prefix rule that accepts `-T4` and `-p80`. Real nmap reads `-oJ file` as `-o J`: it writes a
  file called `J` and treats `file` as a target. The row was wrong; the tool is silent about it.
- **The eWPTX `Content-Length: 4` is deliberate.** In a request-smuggling probe the body is the
  payload and the mismatch is the point. It is documented as such and must not be "fixed".

### 9.6 The 33 Minor findings, checked a second time against today's tree

The fixes of the first pass were verified once more, this time by a read-only pass that re-read
every Minor finding in [`AUDIT-2026-09-18.md`](AUDIT-2026-09-18.md) and looked for the defect in
the file rather than for a correction in its record. Result: **30 corrected, 2 refuted, 1
partial** and none that needed a lab this environment does not have.

- **Refuted 1 — the SPL field.** `New_Process_Name` is real (Splunk Lantern queries
  `sourcetype="wineventlog:security" EventCode=4688 | stats … BY New_Process_Name`, and the
  add-on's own manual lists `new_process_name` among the fields it adds for 4688). The name that
  does not exist is `Parent_Process_Name`, which is the half the audit got right, and that is
  what the query now uses. See §9.4.
- **Refuted 2 — the SAML link.** The OASIS committee URL the audit reported as a 404 answers
  **200** today, and did not reproduce on re-check; nothing was changed to "fix" it.
- **Partial — the SecLists wordlist.** `eWPT/methodology/01-reconnaissance.md` cited the PHP
  backdoor wordlist without its subfolder, and the bare name 404s:
  `Discovery/Web-Content/CommonBackdoors-PHP.fuzz.txt` → **404**, while
  `Discovery/Web-Content/Programming-Language-Specific/CommonBackdoors-PHP.fuzz.txt` → **200**.
  The sentence now carries the full path, and the record that claimed the bare name "exists" was
  corrected with it — a record is a claim about the file, and it was wrong about its own line.
- **Three adjacent defects, found by the same pass and fixed here.** `slugify()` dropped the
  underscore everywhere, so `foo_bar` slugged to `foobar` while GitHub keeps it. Latent today —
  of this repository's **2,807** headings, 49 contain a markdown marker and exactly one contains
  an underscore, and none of the 11 in-repo anchors points at a marker heading — which is
  precisely why a reading had not caught it: the first heading with an underscore would have had
  its real anchor rejected. It now removes only an underscore *pair* that can open and close
  emphasis, which matches `github-slugger` on every test case except the ones where GitHub
  renders emphasis first. A verification record in `eCTHP/methodology/05-detection-engineering.md`
